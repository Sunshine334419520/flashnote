## 1. 统一心智模型：三层不是三种存储

手册 2.3.1 的三层模型（工作记忆 / 短期记忆 / 长期记忆）对应人脑记忆研究的经典框架（Atkinson–Shiffrin 模型）。作为 agent 工程师，关键在于意识到：**这三层在工程上根本不是三种"存储"，而是同一份信息的三种"组织状态"**。

```
模型输出/tool结果（瞬时）→ 上下文历史（本轮会话）→ 持久化存储（跨会话）
   └── 工作记忆 ──┘      └──── 短期记忆 ────┘      └─── 长期记忆 ───┘

每一层只解决一个问题：
  工作记忆 = 现在"放在 prompt 里"的东西 —— 由你控制，唯一有成本的东西
  短期记忆 = 如何压缩/遗忘对话历史 —— 滑动窗口 + 摘要
  长期记忆 = 如何写/查/更新跨会话的事实 —— 生命周期管理
```

**核心认知：真正昂贵的是工作记忆（token 预算），长期记忆的唯一目的是在将来以最低成本"重建"有用的工作记忆。** 所以 2.3.3 的四个决策点，本质上是同一个问题——**"什么信息值得将来再花 token 换回来？"**——在四个环节上的分解。

## 2. 记忆生命周期总览

手册给出的生命周期：

```
创建 → 检索 → 强化（再次用到则提权）→ 衰减（长期不用降权）→ 遗忘
```

逐环补充工程含义：

| 环节 | 做什么 | 关键设计问题 |
|------|--------|--------------|
| **创建 (write)** | 决定是否把一条信息写入长期存储 | 触发的条件是什么？（决策点 1） |
| **检索 (retrieve)** | 决定把哪些记忆放回上下文 | 何时查、查几条、怎么排序？（决策点 3） |
| **强化 (reinforce)** | 记忆被成功复用后提高权重/优先级 | 复用的"成功"如何定义？谁来判定？ |
| **衰减 (decay)** | 长时间未被使用就降低权重 | 衰减曲线长什么样？（指数？线性？） |
| **遗忘 (forget)** | 删除或归档权重过低的记忆 | 是硬删还是软删（归档 + 标记 stale）？ |

记忆的"强化-衰减"机制直接借用**艾宾浩斯遗忘曲线**（Ebbinghaus forgetting curve）的思路——人的记忆不随时间线性衰减，而是**指数衰减**，且每次"被唤醒"会重置曲线。agent 系统同理：每条记忆每被成功检索一次，它的 `last_access_time` 和 `access_count` 都更新，排序时 recency 因子自然给它加权。

## 3. 决策点 1：什么触发记忆写入？

手册列的选项是"每次交互？手动？关键决策后？"，对应三种触发哲学：

| 触发策略 | 做法 | 优点 | 致命缺点 |
|---------|------|------|---------|
| **全量写入** | 每次交互都存 | 实现简单、不丢信息 | **写放大**：噪声淹没信号；检索质量崩坏；存储+向量成本飙升 |
| **手动写入** | 用户显式说"记住"才存 | 零污染、成本最低 | 依赖用户自觉；忘记录入就丢失 |
| **信号触发** | 只在检测到高价值事件时写 | 平衡 | 需要设计"价值判断" |

**核心洞察：写入必须是有条件的，条件就是"这条信息的预期未来价值"。** 可量化为打分函数：

```
write_score = f(重要性, 新颖度, 可复用性, 置信度)
```

真实系统的参照：

- **Stanford Generative Agents**（Park et al., 2023）：每条观察在写入时就打一个 1–10 的 **importance score**，由 LLM 判断（"用户提到自己是咖啡师" → 6 分；"用户今天穿了蓝衬衫" → 2 分）。低分记忆就是将来检索时被淘汰的那批。
- **Mem0**：写入完全由应用开发者显式调用 `add()`，即"手动 + 信号"混合——框架不自己猜。
- **MemGPT / Letta**：用"OS 分页"思路，写入由内存不足/任务需要触发，信息在 main context 和 external context 之间换页。
- **Claude Code 的记忆系统**（可触达的活例子）：写入原则是"只保存**非显而易见**的事实"——不存 git 历史已经记录的东西、不存 repo 结构、不存只对当前对话有用的一次性信息。

**落地建议**：与其纠结"触发时机"，不如写一条**写入选优策略（write policy）**清单，例如：

```
写 → 用户直接表达过的偏好 / 明确纠正过你的行为
写 → 关键决策达成（方案被批准、架构被选定）
写 → 反复出现的失败模式及解决方案
写 → 与现有记忆矛盾的新事实（但标记为待仲裁）
不写 → 能从代码/git/文档重新推导出的信息
不写 → 未经验证的 tool 输出（尤其是外部网络内容）
不写 → 情绪性、低置信度、一次性信息
```

## 4. 决策点 2：如何避免记忆污染？

四个决策点里**最容易被低估**的一个。记忆污染比"记忆缺失"危害更大——缺失只是不知道，污染是**自信地错**，而且错误会随每次检索被"强化"机制放大。

### 4.1 污染源清单

| 污染源 | 场景举例 |
|--------|---------|
| **错误写入** | agent 操作失误后，把错误的"结论"当事实存了 |
| **过期信息** | "用户使用 yarn"被记住，三个月后用户切到 pnpm |
| **矛盾信息** | 新事实与旧记忆冲突，两条并存互相打架 |
| **注入污染** | tool 返回的外部内容（网页/文件）里藏了伪造指令或假事实，被当记忆吸收 |
| **回音室强化** | 错误记忆被反复检索复用，权重越涨越高，越来越"真" |

### 4.2 防御机制（按写入→存储→检索全链路排列）

```
写入时:  ① 置信度分级 —— 只把高置信度结论写入持久层；
         ② 冲突检测 —— 写入前与现有记忆比对，发现矛盾就地处理
存储时:  ③ 来源溯源 (provenance) —— 每条记忆带 source + confidence + timestamp；
         ④ 版本化 —— 不是覆盖，是新增版本，旧版标记 superseded
复用后:  ⑤ 校验反馈 —— 记忆被引用后若被证伪，立即降权/作废
周期:    ⑥ 整合反思 (consolidation/reflection) —— 定期让 LLM 扫描记忆，合并矛盾、淘汰噪声
用户:    ⑦ 可审查性 —— 用户能查看和删除记忆
```

展开几个机制：

**③ 来源溯源** 是性价比最高的一招：

```
source: "user"   → 高优先级，除非被用户推翻
source: "tool"   → 中优先级，tool 输出不可信（可能含注入内容）
source: "model-inferred" → 低优先级，模型推理，最易出错
confidence: 0.9  +  linked evidence 指向证据来源
```

检索结果注入 prompt 时把 source/confidence 一起带上，让模型知道"这条是用户亲口说的，那条是外部网页里读来的"，它自然会区别对待。

**④ 冲突处理** 的三个策略（按一致性需求递进）：

- **last-write-wins**：最新写入覆盖旧的。简单，但可能把对的旧信息覆盖掉。
- **标记待仲裁**：新记忆不覆盖，只标 `conflict: true`，由下次检索时的 LLM 或周期性的整合反思来裁决。
- **版本链 + 权威源**：每条事实保留历史版本和权威来源，冲突时以更高置信度/更高权威源为准。

**⑥ 整合反思** 直接来自 Generative Agents 的 reflection 机制：不是"对话后立刻反思"，而是**攒够一批观察后，用 LLM 把零散记忆提炼成更高层的抽象记忆**，这一步天然会丢弃噪声、合并重复、暴露矛盾。

> **Claude Code 的一条对应原则**：recall 时先验证——"如果一条记忆提到某个文件/函数/flag，推荐它之前先确认它还存在"。这是检索侧的污染防御：即使存储层没防住，读取侧也不盲目采信。

## 5. 决策点 3：如何检索？

手册问了三个子问题：**什么时候检索？检索多少条？如何排序？**

### 5.1 什么时候检索？（检索时机）

| 模式 | 做法 | 适用 |
|------|------|------|
| **总是注入** | 每轮把"核心记忆"都放进去 | 记忆很少（< 几十条）或 system prompt 里有常驻区 |
| **按需触发** | 检测到任务涉及某主题时才查 | 记忆很多，全查会爆上下文 |
| **双层混合** ⭐ | ① 每轮常驻注入"身份级"记忆（用户画像、核心偏好，几条而已）；② 其余按需检索 | **大多数生产系统的正解** |

按需触发的触发信号：

- **query rewriting**：任务文本 → 提取检索 query（甚至拆成多个 sub-query，多路检索）
- **路由判断**：模型先判断"这个任务是否需要外部记忆"（轻量 classifier），需要才查
- **关键词/实体检测**：出现已知实体名（项目名、人名、技术栈）就触发

### 5.2 检索多少条？（top-k 由 token 预算决定，不是拍脑袋定条数）

```
k = 记忆注入预算 / 单条记忆平均 token 数
```

流程：先定"记忆最多占上下文多少 token"（比如 2K–4K），再倒推条数。宁可检索 5 条高相关的，不要检索 20 条把预算吃光。

### 5.3 如何排序？（混合排序）

单维度排序不够，生产系统普遍做**加权融合**：

```
final_score = α · relevance(语义相似度) + β · recency(最近访问) + γ · importance(重要性)

# 或混合检索 (hybrid search)：
RRF(d) = Σ 1 / (k + rank_i(d))   # Reciprocal Rank Fusion，融合 BM25 + 向量得分
```

排序之上还有一层**精排 (re-ranking)**：先用向量+BM25 粗召回 top-50，再用 cross-encoder 或 LLM 对 top-10 精排。代价是增加一次模型调用，质量敏感场景才值得。

> 手册 2.3.2 提到混合检索"实现复杂"，其实本质就是上面的 RRF 公式——并不复杂，20 行代码的事。

## 6. 决策点 4：如何给检索结果分配上下文窗口空间？

这是最体现架构功力的决策点，因为它把记忆问题和 prompt 工程、系统设计绑定在一起。核心矛盾：

```
上下文窗口是稀缺资源，且是零和的 ——
记忆多占 1K token，历史或 tool result 就少 1K。
```

### 6.1 预算定位（对应手册 2.1.2）

```
总上下文（200K）
├── System Prompt       10-20%   ← 静态，可缓存
├── 长期记忆             5-10%   ← 决策点 4 管这块
├── 对话历史            30-50%   ← 滑动窗口 + 摘要
├── Tool Results        20-30%   ← 用后即弃，尽量不占
├── 工作记忆             5-10%   ← 当前任务临时状态
└── 预留空间             5-10%
```

### 6.2 四层分配手段

```
第 1 层  常驻区 (always-injected)    身份级记忆，永远在，占 1-2%
第 2 层  按需检索区 (retrieved)      决策点 3 查回来的，占 3-8%
第 3 层  压缩注入                    检索结果先 LLM 摘要成 "memory brief" 再注入
第 4 层  指针注入 (titles only)      上下文紧张时只注入记忆标题，模型按需再展开详情
```

- **压缩注入**：与其把 5 条原始记忆原文塞进 prompt，不如让 LLM 把它们**针对当前任务压成一段 100–200 token 的"记忆简报"**。
- **指针注入** 是 MemGPT 的核心思想：外部存储当"磁盘"，上下文当"RAM"，模型通过"换页"决定什么时候把哪块记忆调进主存。上下文快满时，把旧对话压成摘要"换出"，把需要的记忆"换入"。

### 6.3 冲突时的降级顺序

上下文即将超限时，按此顺序牺牲：

```
先砍  →  低相关度记忆（检索回来的，没被用到）
再砍  →  老旧对话历史（用摘要替代）
后砍  →  高价值记忆 / system prompt（动不得）
```

## 7. 高级话题

对应手册 2.3.4。三个概念都来自认知心理学（Tulving 的记忆分类），但要转化为工程能力。

### 7.1 程序性记忆（Procedural Memory）——"记住怎么做"

**认知学原型**：人会骑自行车但描述不出操作步骤——这是程序性记忆（技能），区别于"知道法国首都是巴黎"（语义记忆）和"记得上次去巴黎的经历"（情景记忆）。

**Agent 里的对应物**：把**成功的操作序列**存成可复用模式。

```
普通记忆："部署要运行 build"
程序性记忆："要部署这个项目，执行 ① pnpm build → ② 跑测试 → ③ 发布 → ④ 验证版本号"
```

**关键洞察**：手册 2.2 的 **Skill 本质就是程序性记忆的工程化封装**。Skill 的 L1→L4 阶梯（模板→引导→含工具→编排）就是程序性记忆从"一句话"到"完整工作流"的复杂度层级。

**如何构建**：从 agent 的成功轨迹（tool-call trace）中**提取**重复出现的成功序列 → 泛化 → 验证 → 固化为 skill/playbook。

**危险点**：

- **过度泛化**：把一次成功当成普遍规律，换个环境就崩
- **脆性固化**：流程过时了但记忆还在，形成"祖传错误流程"
- **验证缺失**：没验证过的序列被记住，等于存了个 bug

→ 程序性记忆**只记录成功验证过的序列**，且要定期审计是否仍适用。

### 7.2 情景记忆（Episodic Memory）——"完整记一次经历"

**定义**：记录完整的事件上下文，而不是孤立的结论。

```
情景记忆 = { 当时状态 (situation) → 采取的行动 (action) → 结果 (outcome) }
```

**与语义记忆的区别**：

| | 语义记忆 (semantic) | 情景记忆 (episodic) |
|---|---|---|
| 记什么 | 剥离上下文的结论 | 带完整上下文的事件 |
| 例子 | "Windows 托盘图标路径要从 extraResources 取" | "上周修 Windows 图标 bug：assets 放 files 里打包后找不到路径，改用 extraResources 后修复" |
| 用途 | 直接复用结论 | 类比推理："当前情况像上次，上次那么做失败了，所以这次换方案" |

**价值**：这是 agent 从"看过案例"到"有经验"的关键。遇到新任务时，不是查"规则"，而是查"相似的历史事件"，用类比推理决策——这正是经典 AI 的 **基于案例推理 (Case-Based Reasoning, CBR)**。

**与 Reflexion 的关系**：情景记忆是 Reflexion 的**存储底座**。Reflexion 让 agent 反思"哪里错了"，而反思结果（当时的状态 + 错误决策 + 失败原因 + 修正策略）正是写入情景记忆的内容。没有情景记忆，Reflexion 的教训一次用完就丢了。

**记忆整合（Consolidation）**：人脑睡觉时把情景记忆整合成语义记忆。agent 同样可以——定期把一批相似的情景记忆**提炼成一条普适规则**（语义记忆），既提高信息密度，又自动完成去重。这就是决策点 2 里"整合反思"的更深层用途。

### 7.3 记忆一致性（Memory Consistency）——多 agent 共享记忆

**问题场景**：多个 agent（或一个 agent 的多实例）读写同一个记忆库。手册 4.1 的多 agent 协作一旦共享记忆，立刻遇到数据库并发问题。

**三个典型问题**：

```
① 丢失更新 (lost update)
   Agent A 写 "color=amber"，Agent B 写 "color=blue"
   → 最后谁写谁赢，另一个白写，且不知情

② 读写竞态 (read-write race)
   Agent C 读到的记忆，在它读取时已被 Agent D 改掉
   → C 基于过期信息做决策

③ 信仰分歧 (divergent beliefs)
   Agent E 和 Agent F 记住了同一个事实的两个版本
   → 下游汇总时互相矛盾，无法判定谁对
```

**解决方案谱系**（按一致性强度递增）：

| 方案 | 做法 | 代价 |
|------|------|------|
| **事件溯源 (event-sourcing)** | 记忆只增不改（append-only），读时从事件日志重建当前视图 | 存储膨胀，读变慢 |
| **版本化 + 冲突检测** | 每条记忆带版本号，冲突时标记待仲裁，不自动覆盖 | 需要仲裁机制 |
| **单一写者** | 记忆写入收敛到单一 agent（curator/记忆管理员），其他 agent 只读 | 引入中心瓶颈 |
| **带权威源的主数据** | 事实的主副本在特定 agent/系统里，冲突以主数据为准 | 需要定义主数据归属 |
| **周期收敛 (reconciliation)** | 各 agent 各自写，但定期由协调者 merge + 去重 + 仲裁 | 收敛有延迟 |

**工程判断**：强一致在记忆系统里通常不值得。**最终一致性 (eventual consistency) 往往就够**——关键决策的关键记忆用"单一写者 + 权威源"，一般性记忆允许短期不一致，靠周期整合反思收敛。这个"按重要性分级的一致性"思路，和决策点 1 的价值打分是一致的。

## 8. 五个机制闭环

四个决策点 + 三个高级话题，组合起来是一个自洽的闭环：

```
任务进行中
  │
  ├─[决策点1] 这个观察值得写吗？→ 值得 → 打重要性分，带来源，写（含冲突检测）
  │
  ├─[决策点3] 现在需要查记忆吗？→ 需要 → 混合检索 top-k（受决策点4预算约束）
  │           记忆被复用成功 → [强化] 提权
  │           记忆被引用但证伪 → 降权 + 更新来源
  │
  ├─[决策点4] 检索结果压缩/指针化，挤进上下文预算
  │
  ├─[高级: 情景] 遇到失败/成功 → 反思 → 写入完整"状态-动作-结果"
  ├─[高级: 程序] 同一成功序列出现多次 → 提取成 skill/playbook
  │
  └─[周期] 整合反思 → 情景整合成语义、矛盾仲裁、噪声淘汰
     持续衰减 → 低频记忆降权 → 遗忘（软删/归档）
```

任何一个环节做不好，其他环节都会受影响——比如写入选优没做好（决策点 1），检索就会被噪声淹没（决策点 3）；没有衰减机制，过期记忆会一直占着排序高位污染决策。

## 9. 练习与实验

在手册 2.3.5 练习 5 的基础上，加强版验收点：

```
练习 5+：
① 在写入口实现"来源溯源 + 冲突检测"（决策点2）
② 实现排序时的时间衰减因子（强化/衰减）
③ 故意写入一条错误记忆，验证"整合反思"能否在 N 轮内纠正它

实验 A：写入选优对比
  全量写入 vs 价值打分写入，各跑 50 轮对话
  → 对比：检索准确率、每次检索的平均噪声、存储量

实验 B：排序权重对比
  只用语义 vs 语义+recency+importance 加权
  → 对比：下游任务完成率

实验 C：程序性记忆提取
  让 agent 重复做同一类任务 5 次
  → 从轨迹中自动提取成功序列 → 固化成 skill
  → 验证第 6 次任务是否更快/更稳
```
